# Deploying SlotFill to AWS (Phase 7)

Everything here is **prepared and verified offline**: Docker images build and run, and the CDK app typechecks, passes its assertion tests and synthesizes CloudFormation for staging and production. **Nothing has been deployed.** Deploying needs your AWS account, and these steps are yours to run.

## What gets created (`infra/lib/slotfill-stack.ts`)

- **KMS** key with rotation. It encrypts RDS, Secrets Manager, ECR and the SNS topics.
- **Network:** a VPC across 2 AZs with public, app (private with NAT) and db (isolated) subnets.
- **RDS PostgreSQL 16:**
  - private, KMS-encrypted, `rds.force_ssl=1`, automated backups;
  - production adds Multi-AZ, 30-day backups and deletion protection.
- **Secrets Manager**, all generated by the stack:
  - the RDS owner credentials;
  - the `slotfill_app` password;
  - `SESSION_SECRET`;
  - `ENCRYPTION_KEY` (64 hex chars, retained even if the stack is deleted).
- **ECR** repositories `slotfill-<stage>-api` / `-web` (scan on push, KMS).
- **ECS Fargate**, no public IPs, deploy circuit breaker:
  - `api` and `web` services, 2 tasks each in production;
  - `worker`, 2 tasks in production (pg-boss coordinates them);
  - a one-off **release** task: DB bootstrap plus `prisma migrate deploy`, run as the owner.
- **Load balancer:** HTTP redirects to HTTPS (TLS policy _recommended_). `/api/*` goes to the api; everything else goes to web. Health checks use `/api/v1/health/ready` and `/login`.
- **AWS WAF:**
  - a per-IP rate limit on `/api/v1/auth` (100 per 5 min) and globally (2000 per 5 min);
  - the AWS Common and Known-Bad-Inputs managed rule sets.

  This also makes the auth and webhook rate limits hold across several API tasks; the in-process limiter is per task.

- **SNS topic for inbound SMS** (KMS), which End User Messaging is allowed to publish to, with an HTTPS subscription to `https://<domain>/api/v1/webhooks/sms/aws`.
- **CloudWatch:**
  - log groups (1 year in production, 1 month in staging);
  - 9 alarms: ALB 5xx, API 5xx, unhealthy API/web targets, API/worker CPU, worker not running, DB CPU, DB free storage;
  - all alarms notify an SNS topic, with optional email.
- **Task role** limited to `sms-voice:SendTextMessage` and `ses:SendEmail`/`SendRawEmail`.

## One-time prerequisites (in your AWS account)

1. **Sign the AWS BAA** in AWS Artifact _before any real PHI_. Use HIPAA-eligible services only (everything above is).
2. **Domain and certificate:** request an ACM certificate for e.g. `app.yourdomain.com` in the deploy region.
3. **SES:**
   - verify the sending domain;
   - request production access (to leave the sandbox);
   - choose `EMAIL_FROM`, e.g. `SlotFill <no-reply@yourdomain.com>`.
4. **SMS (AWS End User Messaging SMS):**
   - get an origination number per clinic: toll-free (needs toll-free verification) or 10DLC (needs brand and campaign registration; see the open decision in `decisions.md`);
   - enable **two-way SMS** on each number with the stack's `InboundSmsTopicArn` output as the destination;
   - SNS will send a subscription confirmation to the webhook, and the API confirms it automatically.
5. **Tooling:** Node 24, Docker, the AWS CLI with credentials, and the CDK CLI (installed by `npm install` in `infra/`).

## Deploy

```bash
cd infra
npm install                   # Windows: needs long paths enabled, or use the Docker command below
npx cdk bootstrap             # once per account/region
CTX="-c stage=staging -c domainName=staging.yourdomain.com \
     -c certificateArn=arn:aws:acm:...:certificate/... \
     -c emailFrom='SlotFill <no-reply@yourdomain.com>' \
     -c alarmEmail=you@yourdomain.com [-c drchronoSecretArn=arn:aws:secretsmanager:...] -c imageTag=$(git rev-parse --short HEAD) \
     -c account=123456789012 -c region=us-east-1"
npx cdk deploy $CTX           # creates everything; services wait for images
```

**Images** (push with the same `imageTag`; staging keeps the dev tools pages):

```bash
aws ecr get-login-password | docker login --username AWS --password-stdin <account>.dkr.ecr.<region>.amazonaws.com
docker build -f docker/api.Dockerfile -t <ApiRepositoryUri>:<tag> . && docker push <ApiRepositoryUri>:<tag>
docker build -f docker/web.Dockerfile --build-arg NEXT_PUBLIC_DEV_TOOLS=true -t <WebRepositoryUri>:<tag> . && docker push <WebRepositoryUri>:<tag>
# production: omit --build-arg (dev pages then return 404)
```

**Release** (database bootstrap and migrations). Run it before each deploy that has migrations:

```bash
aws ecs run-task --cluster <ClusterName> --launch-type FARGATE --task-definition <ReleaseTaskDefinition> \
  --network-configuration "awsvpcConfiguration={subnets=[<AppSubnets>],securityGroups=[<ReleaseSecurityGroup>],assignPublicIp=DISABLED}"
```

Then point DNS for the domain at the `LoadBalancerDns` output.

**First platform admin** (your own account for the `/admin` console, once SES can send). Run the script with the **API** task definition, so it uses the app's database role and email settings. The invite link is emailed, never printed:

```bash
aws ecs run-task --cluster <ClusterName> --launch-type FARGATE --task-definition <ApiTaskDefinition>   --network-configuration "awsvpcConfiguration={subnets=[<AppSubnets>],securityGroups=[<ApiSecurityGroup>],assignPublicIp=DISABLED}"   --overrides '{"containerOverrides":[{"name":"Api","command":["pnpm","--filter","@slotfill/api","admin:create-platform-admin","you@yourcompany.com"]}]}'
```

Open the emailed link, choose a password, sign in, and enroll MFA. From then on you onboard clinics in the browser (**Admin → Clinics → Add a clinic**). `<ApiTaskDefinition>` and `<ApiSecurityGroup>` are stack outputs.

## Staging with synthetic data

Run the seed through the release task definition with a command override. It refuses to run when `APP_ENV=production`:

```bash
aws ecs run-task ... --overrides '{"containerOverrides":[{"name":"Release","command":["sh","-c","export MIGRATE_DATABASE_URL=\"postgresql://$OWNER_USER:$(node -e \"process.stdout.write(encodeURIComponent(process.env.OWNER_PASSWORD))\")@$DB_HOST:$DB_PORT/$DB_NAME?sslmode=require\" && pnpm --filter @slotfill/api db:seed"]}]}'
```

To run the **Phase 5 scenario with a real phone** (the Phase 7 "done when"):

1. Set a demo clinic's number to your AWS origination number, and give one synthetic patient your test phone. Use a SQL session as the owner, e.g. a temporary bastion or an ECS exec into the release task:
   ```sql
   UPDATE tenants SET sms_number = '+1<aws-number>' WHERE name = 'Maple Family Clinic';
   UPDATE patients SET mobile_e164 = '+1<your-phone>' WHERE id = '<a waitlisted patient>';
   UPDATE mock_patients SET mobile_e164 = '+1<your-phone>' WHERE id = '<its ehr_patient_id>';
   ```
2. Follow the Phase 5 steps in `USAGE.md`. Staging has `/dev/ehr`, because the web image was built with dev tools and `APP_ENV=staging` mounts the dev API routes.
3. You receive the offer by SMS. Reply **YES** from your phone; it arrives via End User Messaging, then SNS, then the webhook.

## Operational notes

- **Rollback:** ECS circuit breakers roll back failed deploys. Migrations are forward-only; write them to be backward compatible with the previous app version.
- **Scaling:** api and web are stateless. The worker can run several tasks (pg-boss uses row locking; stately queues keep one EHR sync per clinic). Job heartbeats recover work from a dead task within about 30 s.
- **Logs** never contain PHI (IDs only, path-only request logs). Retention: 1 year in production.
- **Not covered yet:** a CI pipeline that builds, pushes and runs release then deploy (the commands above are its steps); RDS Proxy; per-tenant KMS data keys for field encryption (today one key from Secrets Manager).
